## Approved new selection: acceptance contract

The user-facing route must be **Plugins → review → NEW selection → preview →
explicit confirmation → restart**. Only supported, unambiguous delivered-bundle
rows qualify. Confirm exact schema-valid settings; do not guess attribution from
old names/paths or silently substitute candidates. Pins, rights conflicts,
unsupported/ambiguous rows and owner conflicts remain blocked for the user's own
action. No attribution, pin, grant or ownership takeover.

Keep two backup roles distinct:

1. Immutable, hash-protected **original valid pre-v2 plugin state**, before the
   first mutation including startup. This baseline backup implementation exists;
   backup conflicts fail closed. Existing v2 state is not invented v1 history.
2. Backup of the **actual current state immediately before new selection**,
   required by the newly approved path. An old original backup is no substitute.

These are plugin-state safeguards, not a complete rollback of all profile data.
The release notes must retain full-profile backup advice and warn that old
executables cannot read the v2 plugin envelope. Downgrade uses a separate full
profile compatible with the older release, not the live upgraded profile;
subsequent changes are not automatically preserved.

The implementation has local old-profile replay evidence for 1.0.0/1.0.1,
including two restarts, separately from the historical baseline above. Final
acceptance must bind upgrade results to the integrated source and delivered
packages: install-directory changes, safe previews/exact settings, both backups,
blocked/conflicting cases and two restarts. Preserve titles, selected/disabled
sources and unrelated state. A backup alone is not legacy-candidate recovery.
