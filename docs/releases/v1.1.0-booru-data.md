# Booru data: upgrading and older versions

Status: preparation note for the MeowChan 1.1.0 development line, written
12.11.2026. It describes the data the Danbooru feature adds and what an upgrade or a
return to an older version does with it. It is not a release note and does not say
that 1.1.0 is released or release-ready. For the user-visible behaviour see
[Danbooru search, watchers and offline use](../Help.md#danbooru-search-watchers-and-offline-use).

## What is added

- **One new profile file, `booru-catalog.json`,** next to the other profile files.
  It is created when Danbooru data is saved for the first time (a first search
  result that is saved, a watcher, a loaded post). Until then it does not exist, and
  the app reads a missing file as an empty catalog. The upgrade itself creates no
  Danbooru file and runs no migration step.
- **What the file holds** (schema version 1):
  - **Posts**: Danbooru post id, the post link, the provider rating, score and
    favorite count, the time the post was created, the source tags with their
    categories, the media variants Danbooru offers (original, sample, preview, each
    with address, size, dimensions and checksum when given), Danbooru's own free-text
    source, the deleted and banned flags, and when MeowChan first and last saw the
    post. Which of these values Danbooru actually sent is recorded, so a value that
    was not sent stays distinguishable from an empty one.
  - **Findings**: where a post was found (search, single post or a watcher with its
    id and search) and when. A post keeps all its findings.
  - **A link to the local file** once the original is downloaded. The file itself
    stays where the normal download saved it.
  - **Watchers**: id, search, state, creation and last check time, wait time and
    error code, the starting point and progress of the checks, and the post ids
    already seen.
- **What it never holds:** your own tags, credentials or any other part of the
  archive. Source tags (Danbooru's) and your own tags are stored separately.
- **New bundled plugin.** The official Danbooru plugin
  (`meowchan.official.danbooru`) is a new entry in the bundled plugin inventory.
  At first start it appears as a new plugin in the plugin state, like the other
  official plugins, and is enabled by default. It is a post-search source and is not
  registered as a board or thread source.

## What stays unchanged

An upgrade does not read, rewrite or delete any existing profile file: archive,
media manifests, session and download state, rules, settings, plugin state and your
own tags. A profile that never uses Danbooru never gets the new file. The core test
`NewBooruFileIsAnAdditiveOfflineMigrationForAnExistingProfile` checks that an
existing profile file stays byte-identical when the catalog is read and written.
Downloaded Danbooru originals are ordinary local media files. Removing a Danbooru
watcher marks its record as removed and keeps all posts, findings and file links
(`RemovingWatcherKeepsWatcherClaimsAndLocalPost`).

## How the file is protected

- Each write goes to a temporary file in the profile folder and replaces the
  catalog in one step, under the profile lease. A successful write leaves no
  temporary file.
- A catalog that is malformed, larger than 128 MiB, contains duplicate posts,
  findings or watchers, or carries a schema version this app does not know is
  **refused, not treated as empty**. Danbooru features then report an error, and the
  file is not overwritten (`MalformedAndFutureCatalogsFailClosed`,
  `OversizedCatalogFailsClosedBeforeDeserialization`,
  `DuplicatePostFindingAndWatcherIdentitiesFailClosed`).
- Growth is limited by the setting "Danbooru catalog limit (MiB)" (Settings, Advanced: plugin process
  limits; default 32, allowed 8–128). A write that would exceed it fails and writes nothing; from 75 % of
  the limit the watcher area shows a warning. Lowering the setting never makes an existing catalog
  unreadable, because reads are bounded by the fixed 128 MiB ceiling.
- As always before an upgrade: close MeowChan and keep a complete profile backup.
  The backup includes `booru-catalog.json` when it exists.

## Going back to an older version

- **Versions before 1.1.0 do not know `booru-catalog.json`.** It is a separate file
  that those versions neither read nor write, so it stays unchanged on disk and is
  ignored. Danbooru searches, watchers and the Danbooru post information are not
  available there.
- **Saved files are not deleted** by going back. Whether an older version lists a
  downloaded Danbooru file in its own views is not promised, because older versions
  have no Danbooru item type.
- **Coming forward again:** 1.1.0 picks the file up again when it still has schema
  version 1. A file written with a later schema version is refused as described
  above and left untouched.
- The general rule of [Upgrading and backups](../Help.md#upgrading-and-backups)
  still applies: a supported return to an older version means restoring a complete
  backup made before the upgrade, to a separate location, not mixing newer data into
  an older profile.

## What this note does not claim

Only the unit tests named above and the plugin packaging checks were run for these
statements. No upgrade of a real published profile with Danbooru data, no downgrade
run and no run of an older version against a profile that holds
`booru-catalog.json` has been performed. The plugin-state behaviour of an older
version that does not ship the Danbooru plugin was not exercised. The integrated
upgrade check (package B9 of the 1.1.0 Booru work plan,
`docs/architecture/gesamtprogramm-2026-10-31/pakete/1.1.0-booru-arbeitsplan-2026-11-12.md`)
has to cover these cases.
